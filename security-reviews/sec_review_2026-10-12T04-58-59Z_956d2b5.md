## Findings

### Finding 1: HEAD still does not compile — three of eight contracts fail — `contracts/v1/ergonames_v1_reveal.es:162`

- Severity: High
- Confidence: 1.0
- Category: build_integrity
- Description: Commit `956d2b5` fixed the registry (`validSubNameRegistryBoxOut` reference, stray `))`) but three contracts still fail to compile, confirmed with `@fleet-sdk/compiler` 0.12.0:
  1. `contracts/v1/ergonames_v1_reveal.es:162` — `validValueConservation` uses `ergoNameIssuanceBoxOut` (capital "N") while the mint declares `ergonameIssuanceBoxOut` (lowercase "n", line 94); the identifier is undefined and the script cannot be type-checked. Independently, `validValueConservation` (lines 161-163) is dead code: it is not included in the mint's `allOf` (lines 165-172). As written it also assumes no extra inputs (`SELF.value == issuance + fee + miner` holds only when the tx fee and any added inputs balance out), so simply wiring it in without accounting for that would break valid mints.
  2. `contracts/v1/ergonames_v1_collection.es:157` — the refund path still references `ergonameCollectionTokenAmount`, which was renamed to `collectionTokenAmount` at line 43; the identifier is undefined.
  3. `contracts/v1/ergonames_v1_reveal_proxy.es:102` — missing comma after `(revealBoxOut.tokens.size == 1)`; the parser reads the following `(revealHash == revealBoxHash)` as an array application.
  These failures sit in the reveal fee/minimum logic, the collection refund accounting, and the token-payment guard. As with the first review, a revision that does not compile has no deployable artifact; if the genesis is built from a hand-patched copy, the deployed bytecode is not the reviewed source, and edits on exactly these lines (a renamed variable in refund accounting, a register check, a boolean list) are where silent semantic drift happens.
- Exploit Scenario: The genesis build fails outright. Alternatively, the three errors are fixed ad hoc under time pressure — e.g. "fixing" `collection.es:157` by reintroducing a differently-computed amount variable rather than renaming, changing the refund accounting that restores the collection token, or wiring in `validValueConservation` as-is and making every (or no) mint differ from what was reviewed. A third party cannot reproduce the deployed bytecode from the published source.
- Recommendation: Fix the three sites to their evident intent (`reveal.es:162` → `ergonameIssuanceBoxOut`; decide explicitly whether `validValueConservation` is enforced — and if so, extend it for extra inputs/tx fee — or delete it; `collection.es:157` → `collectionTokenAmount`; add the comma at `reveal_proxy.es:102` while keeping the `tokens.size == 1` check). Re-add the compile check (the repository's `genesis_compile_check.mjs` was removed and never reinstated) as a required CI step before any genesis build, and recompute derived addresses/hashes after the fixes.

### Finding 2: The name-token supply cap still requires two units, but the second unit's destination is no longer constrained — `contracts/v1/ergonames_v1_registry.es:308`

- Severity: High
- Confidence: 0.9
- Category: token_supply / protocol_integrity
- Description: `validTokenLimit` in the mint path still requires the total supply of the minted name token to be exactly `2L` (`outputs_sum == 2L`, `registry.es:294-309`). That cap made sense when the mint also created the subname registry box, which held the second unit and was fully validated. Commit `1cf79b5` removed the subname registry output (the `validSubNameRegistryBoxOut` block is commented out and no longer in the mint's `allOf`), so the second unit now has **no sanctioned home**. The per-box check pins exactly one unit in the issuance box (`ergoNameIssuanceBoxOut.tokens(0) == (ergoNameTokenId, 1L)`, line 261), so the remaining unit must be minted into another output. The outputs that can carry it are the fee box (`OUTPUTS(2)`, only its script hash is checked), the registry box (`OUTPUTS(1)`, where only `tokens(0)` is pinned), or the transaction-operator fee box (`OUTPUTS(4)`, only its value is checked); if the consensus allows a box to carry two entries of the same token id, it could also be appended in the issuance box. The destination is chosen by whoever builds the mint transaction, and the mint path is permissionless — it requires no signature from the name's owner — so a third party can snipe a revealed name, mint it, and place the second unit of the name token into a box they control. (The ERG amounts themselves remain pinned by `validFee` + `validChange` + the balance equation: the payment is exactly the oracle price and the tx fee must be zero; the defect is the duplicate token, not ERG value.) The result is that the ownership token for every name is not unique: two units exist, and off-chain resolution or marketplaces that identify the name's holder by "(tokenId, 1)" can no longer distinguish the user's NFT from the extra copy.
- Exploit Scenario: Mallory watches the mempool/chain for a reveal box (or any name she covets), builds the mint transaction herself (she can obtain the AVL insertion proof and supply the required context variables), mints the name to the victim's public key exactly as the contract requires — and places the second unit of the name token in her own operator-fee output. She now holds a box containing the same token id (and can freely copy the EIP-4 registers), a counterfeit ownership token she can attempt to sell or use to confuse resolvers, while the victim also holds "the name". Even without snipe intervention, whichever party builds the mint (e.g. the operator bot) necessarily places the extra unit in a box outside the user's control.
- Recommendation: For the subname-less launch, cap the supply at one: change `outputs_sum == 2L` to `== 1L` (the existing per-box check already requires that single unit to be in the issuance box), or remove `validTokenLimit` and rely on the strict per-box token check. If a second unit is ever wanted again, it must be reintroduced together with a fully validated bound destination (the subname registry output check).

### Finding 3: The issuance box is no longer bound to the user's pre-commitment, so the mint executor controls the artwork metadata — `contracts/v1/ergonames_v1_registry.es:259`

- Severity: Medium
- Confidence: 0.9
- Category: data_validation / metadata_integrity
- Description: Commit `956d2b5` removed the `issuanceBoxHash` from the reveal's data shape (`reveal.es:19`) and removed the check `issuanceBoxHash == blake2b256(ergoNameIssuanceBoxOut.bytesWithoutRef)` from `validErgoNameMint` (it was the final element of the `allOf` at `registry.es:259-263`). Previously the reveal box — whose contents are fixed by the reveal proxy's `revealBoxHash` at proxy creation — committed the entire expected issuance box (owner, value, tokens, all registers) by hash, so the minted NFT was exactly what the user prepared. What remains checked is: owner equals the receiver public key (line 260), `tokens(0) == (ergoNameTokenId, 1L)` (line 261), R4/R5 exactly the name/description, R6/R7 exact constants, R8 only its size (32 bytes), and R9 only that it exists and its first 26 bytes equal `data:image/svg+xml;base64,` (lines 247-254). Everything after those prefixes is unconstrained. Because the mint path is permissionless, the mint executor can therefore replace the on-chain artwork: arbitrary 32 bytes in R8 (breaking the EIP-4 "SHA256 hash of the picture" correspondence), arbitrary content after the 26-byte prefix in R9 (including a non-image payload or an SVG carrying scripts, which the prefix check does not exclude), and extra tokens appended to the user's NFT. The user cannot refuse or undo this — the reveal box is spent by the mint, and the current registry has no burn/undo path.
- Exploit Scenario: Mallory snipes Alice's reveal box and mints it with R9 holding a `data:image/svg+xml;base64,...` URI whose payload is a malicious SVG (e.g. containing scripts) or simply a different image. The contract accepts it, Alice receives the name NFT displaying Mallory's content, and wallets or explorers that render the on-chain data URI show attacker-controlled content under Alice's name; Mallory also keeps the commit box value (the operator fee). Alternatively, Mallory sets R8 to 32 arbitrary bytes so the advertised artwork hash no longer matches the rendered artwork.
- Recommendation: Restore the pre-commitment chain: put the expected issuance-box hash (or the artwork fields themselves) back into the reveal data and re-add the corresponding check in the registry (`blake2b256(issuanceBoxOut.bytesWithoutRef) == issuanceBoxHash`), so the mint can only produce the box the user committed to. If the frontend cannot pre-compute the full box, then at minimum commit and check the artwork registers (full R8 and R9 equality against values carried in the reveal box). Because the mint can be executed by anyone, any uncommitted field is attacker-controlled.

## Notes

### Note 1: The collection no longer pins its own token ids; correctness now depends on genesis ordering — `contracts/v1/ergonames_v1_collection.es:41`

- Category: design-tradeoff / genesis-config
- Observation: `1cf79b5` replaced the compile-time collection token constants with self-referential reads — `singletonTokenId = SELF.tokens(0)._1`, `collectionTokenId = SELF.tokens(1)._1`, `collectionTokenAmount = SELF.tokens(1)._2` — and both action branches now require index-preserving recreation. The real token ids are still enforced elsewhere (the reveal proxy requires `$ergoNameCollectionSingletonTokenId` in INPUTS(0), and the reveal/registry require `$ergoNameCollectionTokenId` on reveal boxes), so a fake collection box created by a third party with arbitrary tokens cannot mint or refund real reveals and no attacker path exists. But the collection script itself can no longer detect a misordered or wrong-token box; the genesis transaction must create it as `[singleton, collection]`, and the now-unused `singletonTokenId` binding (line 41) is a remnant of the incomplete cleanup.
- Rationale: Dropping the constants was part of the subname-removal simplification; the remaining constants in the proxy/reveal/registry still anchor the genuine ids. Recommend documenting the ordering requirement for the genesis box and either removing the unused binding or restoring an explicit assertion if the ids are known at compile time.

### Note 2: The subname contract and documentation remain after the feature was unwired — `contracts/v1/ergonames_v1_subname_registry.es`

- Category: stale-artifact / documentation
- Observation: The mint no longer creates a subname registry output (the block is commented out in `registry.es:267-292` and removed from its `allOf`), so subnames are unreachable in the launch flow; but `ergonames_v1_subname_registry.es` still exists and compiles, the registry header still lists `$subNameContractBytesHash` and a SubNameRegistry output, the fee comment still mentions `subNameRegistry`, and the whitepaper still documents subnames and the two-unit token binding (which no longer exists). If the subname contract is deployed standalone anyway, the first review's Notes 1-2 (revocation semantics; NFTs not self-authenticating) describe its behavior.
- Rationale: The removal was deliberately partial (the contract file may be kept for a future revival), so this is an artifact/documentation consistency issue rather than a vulnerability. Recommend deleting or clearly marking the unused file, comments and whitepaper sections for this genesis; if subnames return, the token-supply binding from Finding 2 must return with them.

## Limitations

Standing limitations:

- This review does not replace a full manual audit or a penetration test.
- This is static analysis of source text. Nothing was executed, fuzzed, or traced at runtime, so timing-dependent, load-dependent, or infrastructure-dependent issues cannot be confirmed here.
- Confidence scores are the reviewing model's own self-assessment, not a calibrated statistical probability.
- Absence of a reported finding does not mean the code is secure. Safety guardrails built into some models can cause a real vulnerability to be softened, generalized, or left out rather than reported in exploit-level detail, and training-data bias can make some vulnerability classes easier for a model to recognize than others. Treat this report as a floor on what a full audit would find, not a ceiling.
- Findings reflect the reviewing model's training data cutoff. A vulnerability tied to a very recently disclosed CVE or library advisory may not be recognized as such.

Review-specific limitations:

- The reviewed revision does not compile (Finding 1), so all logic analysis is of the intended source assuming the three errors are corrected to their evident intent; no ErgoTree from this commit exists to inspect or test.
- Compilation was verified with `@fleet-sdk/compiler` 0.12.0 and type-correct stubs for the injected `$` constants; the real compile-time values (singleton token ids, contract byte hashes) were not available, so byte-level identity with any deployed artifact could not be verified.
- I could not verify the consensus detail of whether a single box may contain two entries of the same token id. It affects only *where* the second unit of Finding 2 can be placed (the issuance box vs. a builder-chosen output), not the fact that the cap is two while the design now admits only one bound holder.
- Off-chain components (bot/transaction builder, frontend, indexer, genesis tooling) are not in this repository and were not reviewed; the attacker-feasibility of Finding 2 and Finding 3 assumes those components' capabilities (AVL proof generation, context-variable construction) are reproducible by a motivated attacker, which the first review also assumed for the bot.
- The gitignored local-only `SECURITY_FINDINGS_GENESIS.md` referenced in the repository history is still absent, so earlier private findings could not be cross-referenced.
- Protocol-level semantics (the "new token id = first input box id" minting rule; token/box serialization and ordering; `AvlTree` equality covering flags/key length; storage rent) were taken from Ergo protocol documentation and practical experience rather than tested on-chain in this review.
