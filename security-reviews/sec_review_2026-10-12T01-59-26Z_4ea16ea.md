## Findings

### Finding 1: HEAD does not compile — three of eight contracts contain four compile-breaking errors — `contracts/v1/ergonames_v1_registry.es:206`

- Severity: High
- Confidence: 1.0
- Category: build_integrity
- Description: The committed revision cannot be compiled to ErgoTree, so no deployable artifact matches the reviewed source. Four distinct errors, all introduced by the latest commit `4ea16ea` ("feat: add fixes for subnames"), and all confirmed with the same `@fleet-sdk/compiler` 0.12.0 the project previously used:
  1. `contracts/v1/ergonames_v1_registry.es:206` — stray `))` after `(registryBoxOut.R4[AvlTree].get == newRegistry)`; a syntax error that removes the closing of the enclosing `allOf(`/`Coll(` that the edit deleted.
  2. `contracts/v1/ergonames_v1_registry.es:232` (also 247–253, 260, 262) — uses `ergonameIssuanceBoxOut` (lowercase "n") while the variable declared at line 125 is `ergoNameIssuanceBoxOut`; the identifiers are distinct, so every use of the issuance box in `validErgoNameMint`/`validEIP4Registers` is unresolved.
  3. `contracts/v1/ergonames_v1_collection.es:128` — `fess(2) >= 10000000L`; `fess` is undefined (typo for `fees`), which breaks the R9 fee-minimum validation added to the reveal path in the same commit.
  4. `contracts/v1/ergonames_v1_subname_registry.es:142` — a stray `}fromBase16("646174613a...")` left after the closing brace of `validSubNameInsertion`; the parser reads it as an "unknown binary operation".
  This matters beyond tooling: the compilation failures sit in exactly the checks that cap minted-token supply, validate the child registry's AVL configuration, and enforce the reveal-box fee minimums. If the genesis is instead built from a separately and informally patched copy of this tree, then the deployed bytecode is not the code reviewed here — the review's conclusions cannot be attributed to it, and post-fix edits to these same lines (parentheses, identifier case, register checks) are exactly where silent semantic drift occurs.
- Exploit Scenario: A genesis/deployment built from this repository fails outright. A more damaging variant: the four errors are hand-fixed under time pressure, and a fix alters semantics of the fee-minimum check or the issuance-box checks (for example, "fixing" the registry line by re-wrapping it differently changes which boxes are compared), producing a deployed contract whose behavior was never reviewed. A third party comparing the published source to the on-chain bytecode cannot reproduce the build.
- Recommendation: Fix the four errors to their evident intent (remove the stray `)`; use `ergoNameIssuanceBoxOut` consistently; `fess` → `fees`; delete the trailing `fromBase16(...)` expression). Re-add the deleted `genesis_compile_check.mjs` to CI so every contract must compile with the real injected constants before any genesis build, and recompute/re-verify all contract addresses and byte hashes derived from the compiled trees after the fixes.

### Finding 2: Collection token order is mutable and permanently assumed, which can disable all reveal refunds — `contracts/v1/ergonames_v1_collection.es:174`

- Severity: Low
- Confidence: 0.8
- Category: state_assumption / token_order
- Description: The refund logic assumes an ordering of the collection box's token list that the creation logic never enforces. Action 1 (reveal creation) checks the re-created collection box with order-agnostic tests — `tokens.exists(t => t._1 == singleton)` and `tokens.exists(t => t == (collectionTokenId, amount - 1))` (`ergonames_v1_collection.es:64-85`) — so the transaction author freely chooses the output token order. However, action 2 (refund) requires the collection output's `tokens(0)` to be identical to `SELF.tokens(0)` and `tokens(1)` to be `(collectionTokenId, amount + 1)` (`ergonames_v1_collection.es:174-175`), and the reveal refund requires `INPUTS(0).tokens(0)._1 == $ergoNameCollectionSingletonTokenId` (`ergonames_v1_reveal.es:189`). If any action-1 spend emits the collection output as `[(collectionTokenId, A-1), (singleton, 1)]` — all still satisfying the action-1 checks — then: (a) every outstanding reveal box fails its refund path, because `INPUTS(0).tokens(0)` is the collection token, not the singleton; and (b) the collection's own action-2 check becomes unsatisfiable, because it would require the same token id at index 0 and index 1. Mints are unaffected (they do not touch the collection box), and the order can be restored by any subsequent action-1 spend that emits the canonical order, but until then (or as long as an attacker re-flips it) all reveal refunds are blocked. The same failure occurs unintentionally if a wallet happens to serialize the collection output's tokens in another order (e.g., sorting by amount).
- Exploit Scenario: Mallory performs one ordinary reveal-box creation and orders the collection output's tokens as `[collectionToken, singleton]`. Alice's pending reveal box — possibly funded with a premium name's price — can no longer be refunded. Mallory repeats the flip whenever a canonical transaction restores the order, keeping Alice's funds stuck in the reveal box; Alice can only recover by minting (if the oracle window happens to hold) or by paying for an extra reveal creation to restore the order herself.
- Recommendation: Enforce the ordering where it is assumed. Either pin the collection output's token order in action 1 (e.g., require the singleton at index 0 and the collection token at index 1), or make the consumers order-agnostic: rewrite action 2 and the reveal refund to test presence of the required tuples (`exists`/fold) and the singleton instead of indexing `tokens(0)`/`tokens(1)`.

## Notes

### Note 1: Parent-burn revocation neither invalidates the child NFT nor shuts down the child registry — `contracts/v1/ergonames_v1_subname_registry.es:404`

- Category: design-tradeoff / revocation semantics
- Observation: Action 3 removes the child's entry from the parent's AVL tree, but the child's subname NFT (in the child's wallet) and the child registry box survive untouched — the child registry always recreates itself with its own token (`validSelfRecreation`), so the parent cannot destroy it. After revocation the child can keep minting new `x~bob~alice` NFTs from the still-functional child registry, and the revoked NFT remains transferable with no on-chain invalidation marker. The parent can then re-mint `bob~alice` to someone else with a fresh token, so two live child registries can carry the same name. Validity is defined by the parent's tree; clients that do not resolve through it can be misled by stale assets.
- Rationale: The omission of a burn requirement is inherent to the design rather than an oversight: the contract cannot force an NFT held in the child's wallet into the revocation transaction, and the child registry can never be destroyed by its own script. The whitepaper (§6) scopes revocation to "the parent's authority over its namespace," i.e., resolution from the parent. Recommend documenting this explicitly for wallets/marketplaces/indexers: a subname is valid only while its token id is the value stored under its hash in the canonical parent registry's tree.

### Note 2: Subname NFTs are not self-authenticating; counterfeit subtrees can be minted in a parallel namespace — `contracts/v1/ergonames_v1_subname_registry.es:105`

- Category: design-tradeoff / authenticity
- Observation: A subname mint only requires `INPUTS(0)` to hold the same token that the registry box itself carries (`validParentErgoName`, lines 103–108); the registry's "singleton" is that token. Anyone can mint their own token, create a same-script registry box carrying it with `R6 = "alice"`, and mint subname NFTs with correct EIP-4 registers (`~bob~alice`) without Alice's involvement. Such a subtree is unreachable from the canonical root registry, so a resolver that walks the canonical tree rejects it — but a naive client that trusts the NFT's EIP-4 name/description cannot distinguish it from a real subname, and nothing on-chain binds a subname NFT back to the root registry.
- Rationale: Free, permissionless per-name subname minting is deliberate (whitepaper §6), and on-chain binding is by token custody within each registry rather than by script-level lineage. This is the same trust model as any NFT: the EIP-4 name field is not exclusive, and resolution must walk the canonical chain (root registry tree → parent name token → child registry → subname hash → token id). Recommend stating this in integrator documentation.

### Note 3: Token-payment vestige is still accepted by the reveal flow although token payments are disabled — `contracts/v1/ergonames_v1_reveal.es:194`

- Category: accepted-risk / disabled feature
- Observation: Custom token payments are hard-disabled in the registry (the non-default branch returns `false`; `contracts/v1/ergonames_v1_registry.es:411`), but the reveal proxy still forwards a proxy token into the reveal box (`reveal_proxy.es:97`) and the reveal refund returns extra tokens to the user (`reveal.es:194-201`). In a mint, no rule constrains where a token carried into the reveal box goes — the transaction builder can route it anywhere (for example the tx-operator output) — so a user who creates a token-bearing proxy/reveal box (e.g., via a stale frontend build) can lose that token.
- Rationale: The token path is deliberately disabled pending a redesign (code comments, and the hardening history's "token payments are DISABLED at genesis"). Until it is rebuilt, consider also rejecting token-bearing reveal boxes at creation (e.g., require `revealBoxOut.tokens.size == 1` in the collection), so the disabled feature cannot silently strand user assets.

## Limitations

Standing limitations:

- This review does not replace a full manual audit or a penetration test.
- This is static analysis of source text. Nothing was executed, fuzzed, or traced at runtime, so timing-dependent, load-dependent, or infrastructure-dependent issues cannot be confirmed here.
- Confidence scores are the reviewing model's own self-assessment, not a calibrated statistical probability.
- Absence of a reported finding does not mean the code is secure. Safety guardrails built into some models can cause a real vulnerability to be softened, generalized, or left out rather than reported in exploit-level detail, and training-data bias can make some vulnerability classes easier for a model to recognize than others. Treat this report as a floor on what a full audit would find, not a ceiling.
- Findings reflect the reviewing model's training data cutoff. A vulnerability tied to a very recently disclosed CVE or library advisory may not be recognized as such.

Review-specific limitations:

- The reviewed revision does not compile (Finding 1), so all logic analysis in this report is of the intended source assuming the four errors are corrected to their evident intent. No ErgoTree from HEAD exists to inspect or test.
- Compilation was verified with `@fleet-sdk/compiler` 0.12.0 and type-correct stubs for the injected `$` constants; the real compile-time constant values (singleton token ids, contract byte hashes, multisig expressions) were not available, so byte-level identity with any deployed artifact could not be verified.
- Off-chain components — the bot/tx-builder, frontend, indexer, and the deployment/genesis tooling that computes the `$` constants, reveals, and issuance-box hashes — are not in this repository and were not reviewed. Assumptions about them (e.g., canonical token ordering by the tx builder, consistency between frontend-computed reveal numbers and the registry's arithmetic) are flagged where relevant but unverified.
- The gitignored local-only file `SECURITY_FINDINGS_GENESIS.md`, referenced by the `.gitignore` history ("never push to this public repo"), is not present in this checkout, so earlier findings could not be cross-referenced.
- Protocol-level semantics (the Ergo token-minting rule that a new token id equals the first input box's id; box/token serialization and ordering; `AvlTree` equality covering flags/key length; `creationHeight` constraints; storage rent) were taken from Ergo protocol documentation and practical experience rather than tested on-chain in this review.
