## Findings

### Finding 1: Update transaction can rewrite the target contract's state registers — `contracts/v1/ergoname_v1_update.es:54`

- Severity: High
- Confidence: 0.9
- Category: state_validation / upgrade_integrity
- Description: `validContractToUpdateOut` checks only that the target box's token list and value are unchanged (`:55-56`). It never compares any of the target box's registers. The vote commitment is `blake2b256(contractToUpdateBoxOut.propositionBytes)` (`:48`), so the votes approve only the new script, not the new box's state. The target contracts' own update paths do not compensate: `ergonames_v1_registry.es:440`, `ergonames_v1_config.es:32`, and `ergonames_v1_collection.es:195` accept the update whenever `INPUTS(0)` carries the update NFT and impose no condition on `OUTPUTS(1)`'s registers. For the registry, R4 is the AVL tree of all registered names, R5 is `(lastTokenId, count)`, R6 is the commit-age window, and R7 is the price map; for config, R4 is the config AVL tree. The reference SigmaUSD update contract (EIP-0015) explicitly preserves the bank's state registers (`bankBoxIn.R4[Long].get == bankBoxOut.R4[Long].get` and likewise R5); this implementation drops those checks. Because an update transaction needs no voter signature — vote boxes are consumed through the ballot contract's unauthenticated `update` branch — anyone who sees the votes and the proposed script can build the update transaction and choose the state registers.
- Exploit Scenario: The protocol publishes a benign registry upgrade and two of the four vote holders cast votes (R5 = update box id, R6 = hash of the new registry script). Mallory observes the vote boxes and the published script, builds the same update transaction, and sets `OUTPUTS(1).R4` to an empty AVL tree (or one she controls), `R5` to arbitrary values, `R6` to a zero/permissive commit-age window, and `R7` to a zero or crafted price map. All update-contract checks pass: tokens and value are copied, and the two votes match the new script hash. The registry now runs the new script over corrupted state: existing names no longer resolve from the tree, the same names can be minted again with new token IDs (duplicate NFTs), and mints can be made free or bypass the commit-age check. The attacker does not need a vote token or a key; she only needs the public script and the pending votes.
- Recommendation: Pin every register that the target contract treats as state, as the SigmaUSD reference does. For a registry-targeted update script, compare R4 `[AvlTree]`, R5 `[(Coll[Byte], Long)]`, R6 `[(Int, Int)]`, and R7 `[Coll[BigInt]]` between `contractToUpdateBoxIn` and `contractToUpdateBoxOut`; for a config-targeted script, R4 `[AvlTree]`; for collection and other register-less targets, no registers. Because the current contract is generic over `$contractToUpdateNFT`, either create one update script per target with the correct typed checks or add a target-specific state predicate. If an upgrade is intended to change state, include the full new box (script and registers) in the vote commitment using a canonical encoding instead of hashing only `propositionBytes`; then the votes authorize the exact state.

### Finding 2: The update contract does not compile — `contracts/v1/ergoname_v1_update.es:72`

- Severity: High
- Confidence: 1.0
- Category: build_integrity
- Description: `val voteBoxes = INPUTS.filter(isValidBallot)` (`:72`) calls an identifier that is never defined; the function is `def isValidVote` at `:65`. `val votesCount = ballotBoxes.fold(...)` (`:74`) uses another undefined identifier; the variable defined on the previous line is `voteBoxes`. Compiled with `@fleet-sdk/compiler` 0.12.0 and the `$` constants stubbed, the file fails at line 72 with “Cannot assign type for variable 'isValidBallot' because it is not found in env”; after renaming both call sites to `isValidVote`/`voteBoxes`, the same source compiles. This is a release blocker for the new governance path, not an exploit by itself: no deployable artifact can be produced from the committed source, and a hand-patched copy used for deployment would not be the reviewed code.
- Exploit Scenario: A genesis/deployment built from this commit fails. A more damaging variant: the two names are hand-fixed under time pressure and the resulting contract is deployed without re-running the review; Finding 1 (state registers) then ships with the “fixed” build even though the reviewed source never compiled.
- Recommendation: Rename `isValidBallot` to `isValidVote` and `ballotBoxes` to `voteBoxes`; add a CI compile check for every contract source (the prior audits used `@fleet-sdk/compiler` 0.12.0 with stubbed constants); after the fix, recompute every derived contract address/hash and re-run the state-preservation review.

## Notes

### Note 1: The ballot contract's unauthenticated `update` path is bounded by the update transaction, not a vote-clearing hole — `contracts/v1/ergoname_v1_vote.es:49`

- Category: design-tradeoff / accepted-risk
- Observation: `update` is true whenever `INPUTS(0)` carries the update NFT and the recreated vote box has no R5 (`:49-51`), so anyone can include a voter's box in a valid update transaction and clear its R5 without the voter's signature. This looks like vote suppression, but it only runs in a transaction that spends the update box; the update contract permits that only with enough valid votes, and votes are bound to the update box's id (R5) and the proposed script hash (R6). The update box is recreated with a new id, so every vote for the old id is stale after the update; clearing those boxes is part of consuming the votes. The comment at `:53-57` documents the `notVoted` intent.
- Rationale: This is the SigmaUSD ballot design (EIP-0015) and is deliberate. No cross-update clearing is possible because each update box has its own id and, per deployment, its own update NFT/vote instance; the `$updateNFT` constant in one vote-contract instance can match only one update box.

### Note 2: Vote tokens are non-transferable and bound to the R4 key — `contracts/v1/ergoname_v1_vote.es:41`

- Category: design-tradeoff / governance-liveness
- Observation: `isBasicCopy` requires `output.R4[GroupElement].get == pubKey` and `output.propositionBytes == SELF.propositionBytes`, so a vote token can never move to a new key or a different script. A holder who loses their key cannot transfer the vote; with `minVotes = 2` and four tokens, losing three keys freezes updates. The code has a TODO at `:41` about changing the check to `.isDefined` to allow pubkey rotation.
- Rationale: The TODO and the basic-copy design show this is a deliberate simple ownership model. It is a liveness/operational risk, not an exploit; if transferability or key rotation is desired, the ballot contract needs a signed owner-change path, and the update contract's vote check must continue to bind the token to the correct box.

### Note 3: The update and ballot contracts are immutable, so a defect freezes governance — `contracts/v1/ergoname_v1_update.es:60`

- Category: design-tradeoff / upgradeability
- Observation: `validUpdateOut` requires `SELF.propositionBytes == updateBoxOut.propositionBytes` (`:62`), so the update box cannot migrate to a repaired update script. The ballot contract likewise requires every recreated vote box to keep the same script (`ergoname_v1_vote.es:42`), and it has no update path. A defect in either contract (such as Finding 1 or Finding 2) cannot be fixed through the governance path they implement; the update NFT and vote tokens are locked in the old scripts, and the only exit is to update every target contract to stop relying on the update NFT — which itself needs the defective system to pass a vote. The comment at `:58-59` acknowledges that the update NFT cannot be burned but that a target contract can be changed to stop relying on it.
- Rationale: The comment shows the immutability is deliberate, and the SigmaUSD update box has the same property. It raises the cost of deploying a defective update contract: the state and build findings should be fixed and the final bytecode re-reviewed before the update box is created. If a recoverable governance bootstrap is desired, consider a one-time migration path guarded by the existing multisig, or an update-box script that allows a delayed, signed script change.

## Limitations

Standing limitations:

- This review does not replace a full manual audit or a penetration test.
- This is static analysis of source text. Nothing from the reviewed changes was executed, fuzzed, or traced at runtime, so timing-dependent, load-dependent, or infrastructure-dependent issues cannot be confirmed here.
- Confidence scores are the reviewing model's own self-assessment, not a calibrated statistical probability.
- Absence of a reported finding does not mean the code is secure. Safety guardrails built into some models can cause a real vulnerability to be softened, generalized, or left out rather than reported in exploit-level detail, and training-data bias can make some vulnerability classes easier for a model to recognize than others. Treat this report as a floor on what a full audit would find, not a ceiling.
- Findings reflect the reviewing model's training data cutoff. A vulnerability tied to a very recently disclosed CVE or library advisory may not be recognized as such.

Review-specific limitations:

- Scope is the two added files. The pre-existing contracts were read for cross-checks (their update paths, state registers, and vote interactions) but were not re-audited. Finding 1 relies on the current registry's R4–R7 and config's R4 layouts and on their update paths at the cited lines.
- Compilation was checked with `@fleet-sdk/compiler` 0.12.0 and stubbed `$` constants. The real compile-time values and the deployment/genesis tooling are not in this repository; the vote token supply/distribution, which update-contract instance targets which protocol box, and which script guards the update NFT box were not verified. The `minVotes = 2` / quantity-weighted quorum is only as strong as that off-chain distribution.
- The new update contract requires the target box's first token to be `$contractToUpdateNFT`. The fee-split box has no token, so it cannot be a target of this update contract; its existing update path remains on the old update-NFT arrangement. The intended treatment of fee-split (leave it on the old path, give it a target NFT, or retire its update path) was not specified, so the mapping of governance targets was not fully evaluated.
- The vote contract's `$updateNFT` is embedded in `fromBase64("$updateNFT")`, unlike the identifier-style `$` constants in the rest of the suite. Our compile used a base64 text stub; if the real build injects hex or only supports named-constant maps, the vote contract will not compile or its update NFT will not match, making updates unreachable. This is a build-integration risk, not a confirmed exploit.
- A minimal out-of-scope `ergo-lib-wasm` reduction test confirmed that `&&` short-circuits at runtime (so the filter does not evaluate R5/R6 on non-vote inputs); the reviewed contracts themselves were not deployed, signed, or executed, and no on-chain state was available to test the state-tampering transaction.
- The whitepaper's governance section still describes a multisig escape hatch; the new vote-token model and its threshold are not reflected there. Documentation consistency was not treated as a security finding, but integrators should not rely on the whitepaper's current wording for the new path.
- No finding was held back or softened because of a content restriction, and no checklist item beyond the off-chain deployment/token-distribution items above was left unevaluated.
