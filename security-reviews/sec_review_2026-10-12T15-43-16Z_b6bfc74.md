# Security Review Report

- **Reviewing agent / model:** DeepSeek V4.1 Flash (provider `opencode-go`, model `deepseek-v4.1-flash`)
- **Reasoning effort / tier:** not applicable — the runtime exposes no reasoning-effort or tier setting to the model
- **Review date and time:** 2026-10-12T15:43:16Z (UTC)

## Scope

File scope: `contracts/v1/ergonames_v1_reveal_proxy.es`, reviewed at commit `b6bfc742d14d61f9e6a1052bd3d946f0e24cd665` (branch `main`, clean working tree). That commit replaces the reveal-box commitment — `blake2b256(revealBoxOut.bytesWithoutRef) == R4` — with a commitment computed over the deserialized R9 fields — `blake2b256(ge.getEncoded ++ secrets.flatMap(identity) ++ fees.flatMap(longToByteArray)) == R4` — because `bytesWithoutRef` includes the output's `creationHeight`, which forced the reveal transaction to reproduce a pre-committed height and caused failing transactions. Project type: Smart contract (ErgoScript / eUTXO).

Verifications performed for this review:

- All 8 contracts compile at this commit with `@fleet-sdk/compiler` 0.12.0 (stubbed `$` constants), including the changed proxy.
- The dropped `creationHeight` is not consumed by any contract: the age checks read the **commit** box's height (`ergonames_v1_commit.es:65-66`, `ergonames_v1_registry.es:137`); no script reads the reveal box's height. Decoupling it is safe.
- Everything else about the reveal box remains pinned across the two scripts that must both accept the reveal transaction: the output script (`ergonames_v1_collection.es:121`), the single collection token (`reveal_proxy.es:122` plus `collection.es:122`), the value (`reveal_proxy.es:120`), and registers R4–R8 (`collection.es:92-96`). Only R9 is left to the new check, which is where this review's finding lives.

## Findings

### Finding 1: The R9 commitment is computed over an ambiguous concatenation, so it does not uniquely fix the reveal box — `contracts/v1/ergonames_v1_reveal_proxy.es:109`

- Severity: Low
- Confidence: 0.8
- Category: data_validation / commitment_encoding
- Description: `validR9Hash` hashes `ge.getEncoded ++ secrets.flatMap(identity) ++ fees.flatMap(longToByteArray)` — a flat concatenation with no element count, no element lengths, and no separators. `secrets` is a `Coll[Coll[Byte]]`, so the commitment depends only on the flattened bytes: any alternative partitioning of the same bytes among `secrets` elements (splitting an element, or inserting zero-length elements) produces the identical hash and passes `validR9Hash`. At reveal-creation time nothing else constrains structure — the collection contract checks only `fees.size == 3` and fee minimums (`collection.es:101-118`); there is no check on `secrets.size` or boundaries. Consequently, a party who knows the preimage (for example, anyone who observes the pending reveal transaction in the mempool, where every committed field becomes public) can build a different, hash-equal reveal box. Downstream mint checks happen to re-impose `secrets(0) = name`, `secrets(1) = secret` (the commit-hash recomputation), `secrets(2) = commitBoxId` (the commit input-id check), and `secrets(3) = imageDataHash` (32-byte equality against the issued artwork), so a divergently partitioned box can never mint — the harm is a **dead reveal box**, not a differently minted name. But the proxy's stated purpose is to guarantee that the created reveal box is exactly what the user committed to, and that guarantee no longer holds: an attacker can lock a user's reveal attempt into a box that can only be refunded (by the user's signature), while keeping the transaction-operator fee for themselves.
- Exploit Scenario: Alice's frontend creates a proxy whose R4 commits to `ge, [Name, Secret, CommitBoxId, ImageDataHash], fees` and broadcasts the reveal transaction. Mallory observes the preimage in the mempool and broadcasts the same transaction with `secrets = [Name, Secret, CommitBoxId, I1, I2]` where `ImageDataHash = I1 ++ I2` (any proper split, e.g. a 16/16 split) and with `OUTPUTS(3)` (the tx-operator fee) redirected to an address she controls. Every check passes — the hash matches because the concatenation is unchanged, `fees.size == 3`, the value/tokens/R4–R8 constraints are untouched. Alice's reveal box now exists, but `secrets(3)` is shorter than 32 bytes, so the registry's `blake2b256(issuance.R8 ++ issuance.R9) == imageDataHash` check can never succeed: the box is permanently unmintable. Alice recovers the value and the collection token only by signing the refund path, paying the extra miner fees and losing the reveal slot (and the commit-box window may expire). Mallory keeps the operator fee (any front-runner could claim that by copying the transaction; the box corruption is what this defect adds).
- Recommendation: Make the committed preimage canonical so that structure is part of the commitment. Either enforce the exact shape on-chain — add `secrets.size == 4` (the current reveal shape) to `validR9Hash`, alongside the existing `fees.size == 3` constraint — or include framing in the hashed bytes, e.g. `longToByteArray(secrets.size.toLong)` and, per element, `longToByteArray(x.size.toLong) ++ x`, plus `longToByteArray(fees.size.toLong)` before the fee encodings. With framing, any structural deviation changes the hash and fails at reveal creation, restoring the "exactly as committed" guarantee.

### Finding 2: Action 1 does not reject a proxy box holding two or more tokens; those tokens are unconstrained and cannot be returned — `contracts/v1/ergonames_v1_reveal_proxy.es:69`

- Severity: Low
- Confidence: 0.75
- Category: token_handling
- Description: `isPayingWithToken = (SELF.tokens.size == 1)` only detects the exactly-one-token case, which fails closed (the reveal box must hold exactly one token, so `revealBoxOut.tokens(1)` is out of bounds and the transaction aborts; such a proxy can only be refunded). A proxy holding **two or more tokens** slips past: `isPayingWithToken` is `false`, `validPaymentToken` is trivially `true` (`reveal_proxy.es:96`), and no check constrains where the proxy's tokens go. The reveal box takes exactly one token (the collection token), and the reveal transaction has no user-payment output — its four outputs are the collection, the reveal box, the miner fee and the tx-operator fee — so extra tokens can only be placed in an output that is not the user's. Whichever party builds the reveal transaction decides the destination.
- Exploit Scenario: A user creates a proxy box that carries two tokens (for example via a stale frontend build, in anticipation of the disabled custom-payment feature). The reveal transaction then necessarily donates those tokens to the collection box's spare slot, the miner-fee output, or the tx-operator output. If the user's own tooling builds the transaction, the tokens land with the operator/miner; if a mempool observer copies the reveal transaction once the preimage is visible, they can redirect the tokens to themselves. The user keeps the tokens only if the proxy is refunded before any reveal transaction lands (the refund path returns all proxy tokens).
- Recommendation: Reject action 1 whenever the proxy holds any token, since the reveal path cannot return tokens to the user: require `(SELF.tokens.size == 0)` in the action-1 branch (or invert `isPayingWithToken` to `SELF.tokens.size > 0`, making the branch fail). Keep the existing `revealBoxOut.tokens.size == 1` guard for the reveal box itself.

## Notes

### Note 1: Dropping the reveal box's creation height from the commitment is deliberate and verified safe — `contracts/v1/ergonames_v1_reveal_proxy.es:106`

- Category: design-tradeoff
- Observation: The previous full-box commitment (`blake2b256(revealBoxOut.bytesWithoutRef)`) included the reveal output's `creationHeight`, so the reveal transaction had to reproduce a pre-committed height; the new R9-field hash omits it entirely. No contract consumes the reveal box's creation height — `ergonames_v1_commit.es:65-66` and `ergonames_v1_registry.es:137` read the commit box's height, and the reveal refund/mint paths do not reference the reveal box's height — so freeing the height removes the reported failure mode without weakening any content of the box.
- Rationale: The commit message documents the goal ("replace reveal box hash with r9 hash … to avoid box height being invalid and failing transactions"); the change achieves it while the box's security-relevant fields remain pinned by the collection contract (script, tokens, value, R4–R8) and by the new R9 check.

## Limitations

Standing limitations:

- This review does not replace a full manual audit or a penetration test.
- This is static analysis of source text. Nothing was executed, fuzzed, or traced at runtime, so timing-dependent, load-dependent, or infrastructure-dependent issues cannot be confirmed here.
- Confidence scores are the reviewing model's own self-assessment, not a calibrated statistical probability.
- Absence of a reported finding does not mean the code is secure. Safety guardrails built into some models can cause a real vulnerability to be softened, generalized, or left out rather than reported in exploit-level detail, and training-data bias can make some vulnerability classes easier for a model to recognize than others. Treat this report as a floor on what a full audit would find, not a ceiling.
- Findings reflect the reviewing model's training data cutoff. A vulnerability tied to a very recently disclosed CVE or library advisory may not be recognized as such.

Review-specific limitations:

- Scope is the reveal proxy file only. Other contracts were consulted solely for cross-checks (the collection's pinning of the reveal output's script/tokens/registers at `collection.es:92-124`, the reveal/registry consumers of R9, and commit-height usage); they were not re-audited here. Full-repository reviews for the current contract set are available under `security-reviews/`.
- The off-chain frontend/bot that computes `revealR9Hash` was not available, so I could not verify that its preimage encoding matches the contract exactly (`ge.getEncoded` canonical compressed encoding, field order, 8-byte big-endian fee encoding, element concatenation without framing). A mismatch would make reveal creation fail (availability), not open a hole.
- Finding 1's exploit path assumes the attacker can observe the pending reveal transaction and rebuild it — standard for public mempools, but not verified against this project's actual deployment or tooling.
- The conclusion that output `creationHeight` is unconstrained for these transactions is based on static usage analysis of the contracts, not on an executed transaction.
- Compilation was verified with `@fleet-sdk/compiler` 0.12.0 and stubbed compile-time constants; the real injected values were not available, so byte-level identity with any deployment could not be checked.
